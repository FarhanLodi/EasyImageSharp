# Contributing to EasyImageSharp

Thanks for taking the time to help. EasyImageSharp is a fully managed imaging library for .NET, and it
holds itself to a few hard rules: **no unsafe surprises for callers, no unreviewed public API, no
non-deterministic tests, and a build that is free of warnings on every supported target framework.**
This document explains how to work inside those rules.

By participating you agree to abide by the [Code of Conduct](CODE_OF_CONDUCT.md). Security issues do
**not** belong in the public issue tracker — see [SECURITY.md](SECURITY.md).

## Getting set up

| Requirement | Version | Needed for |
|---|---|---|
| .NET SDK | **10.0** | building everything; it also builds the `net8.0` leg |
| .NET Runtime | **8.0** | running the tests on the `net8.0` target |
| Python | **3.11+** | regenerating the test fixtures (optional; only when you touch them) |
| Pillow, NumPy | Pillow 11, NumPy 2 | ditto |

Everything else comes from NuGet. There are no native prerequisites for the core library: it is
100% managed code, and the only package reference in the whole repository outside of tests and
benchmarks is ONNX Runtime, in the optional `EasyImageSharp.AI` add-on.

```bash
git clone https://github.com/FarhanLodi/EasyImageSharp.git
cd EasyImageSharp
dotnet restore EasyImageSharp.slnx
```

### Repository layout

```
src/EasyImageSharp/            the core library: codecs, pixel formats, processing, metadata, tensors
src/EasyImageSharp/PublicAPI/  tracked public API baselines, one pair of files per target framework
src/EasyImageSharp.AI/         optional ONNX Runtime add-on (models fetched on demand, checksum-pinned)
tests/EasyImageSharp.Tests/    core tests, including the fixture corpus and the fuzz harness
tests/EasyImageSharp.AI.Tests/ AI add-on tests, running against tiny generated ONNX graphs
samples/AotSmoke/              Native AOT smoke: every codec, metadata path and processing stage
samples/Thumbnailer/           trimming smoke, shaped like a real thumbnail service
benchmarks/EasyImageSharp.Benchmarks/   the BenchmarkDotNet suite behind the README Performance table
benchmarks/corpus/             the script that generates the benchmark inputs; the inputs are not committed
```

`samples/` and `benchmarks/` are deliberately **not** in `EasyImageSharp.slnx`. They single-target
`net10.0` — `PublishAot` and `PublishTrimmed` have no meaning on a multi-targeted project, and the
benchmark host picks its own runtime — and a single-TFM project inside the solution breaks the
solution-wide `dotnet test -f net8.0` leg. They are built and run by path instead, as shown in
[Samples and deployment smokes](#samples-and-deployment-smokes) and [Benchmarks](#benchmarks).

## Build and test

The build treats **warnings as errors** (`Directory.Build.props`), so a build that prints a warning
is a build that fails in CI.

```bash
# Build every project on both target frameworks.
dotnet build EasyImageSharp.slnx -c Release

# Run the whole suite on net8.0 and net10.0.
dotnet test EasyImageSharp.slnx -c Release

# Run one target framework while iterating.
dotnet test tests/EasyImageSharp.Tests -c Release -f net10.0

# Run one test class.
dotnet test tests/EasyImageSharp.Tests -c Release --filter FullyQualifiedName~CodecRoundtripTests
```

Both libraries multi-target `net8.0` and `net10.0`. **Always run both.** The `net10.0` leg picks up
newer BCL intrinsics and API shapes, and it is routine for a change to compile on one and not the
other — for example when a newer overload resolution or a `System.Numerics.Tensors` API only exists
on the newer runtime.

### The AI tests

`tests/EasyImageSharp.AI.Tests` runs entirely offline. The `.onnx` files under `Models/` are tiny
deterministic graphs (identity, 2x nearest upscale, a fixed classifier, and so on) generated by
`Models/gen_models.py`; no model is ever downloaded during a test run. If you change the model
contracts in `src/EasyImageSharp.AI/ImageModelContract.cs`, regenerate them:

```bash
cd tests/EasyImageSharp.AI.Tests/Models
python gen_models.py
```

## Coding style

`.editorconfig` at the repository root is the authority and your editor will apply it. The rules that
matter most, and that reviewers will actually ask you about:

- **File-scoped namespaces.** `namespace EasyImageSharp.Formats;` — never a braced namespace block.
- **`this.` qualification** on every instance field, property, method and event access. This is
  pervasive in the codebase and is not negotiable; it makes the pixel-loop code readable when locals
  and fields have similar names.
- **Four-space indent, Allman braces, always braced.** A single-statement `if` body still gets braces.
- **Line endings** are normalised to LF by `.gitattributes`; do not fight your editor over this.
- **Name the type when it is not obvious** from the right-hand side. `Image<Rgb24> decoded =
  Image.Load<Rgb24>(bytes);` but `var ms = new MemoryStream();`.
- **Private instance fields are `camelCase` with no underscore prefix.** Constants and
  `static readonly` fields are `PascalCase`.
- **Nullable reference types are on** everywhere. Do not silence a nullability warning with `!`
  unless you can explain in a comment why the compiler cannot see the invariant.
- **XML docs on new public API.** `CS1591` is currently in `NoWarn` for the two library projects
  while a backlog of undocumented members is worked through, so the compiler will not stop you —
  reviewers will. Document the *contract*, not the implementation: what it does to the image, what
  the units are, what it throws.

  For scale: of roughly 2,690 tracked public members, about **362 have no XML documentation** (355
  in the core package, 7 in the AI add-on). Over a third of those are the self-describing EXIF tag
  constants in `Metadata/Exif/ExifTag.Known.cs`. To see the current list, build with the suppression
  lifted:

  ```bash
  dotnet build src/EasyImageSharp -c Release -f net10.0 -p:TreatWarningsAsErrors=false -p:NoWarn= --no-incremental
  ```

  Chipping away at that list is a genuinely useful first contribution.

### Things the library does not do

- **No `unsafe` blocks or `Unsafe` shortcuts** where a `Span<T>` will do. Where a hot loop genuinely
  needs one, it must be justified in a comment and covered by a test.
- **No reflection on a hot path, and none at all that a trimmer cannot see.** Both libraries set
  `IsAotCompatible`, which turns the trim and AOT analyzers on and makes `IL2026`/`IL3050` build
  errors. Native AOT and trimming are supported configurations, not best-effort ones.
- **No culture-dependent formatting.** Use `CultureInfo.InvariantCulture` or `FormattableString.Invariant`
  when producing strings that end up in a file or a `ToString()`.
- **No allocation in a per-pixel loop.** Hoist buffers out, rent from `ArrayPool<T>.Shared`, and
  return them in a `finally`.
- **No parallelism that ignores `Configuration`.** Row-parallel work goes through
  `ParallelRowIterator`, which honours `Configuration.MaxDegreeOfParallelism` and
  `Configuration.MinimumPixelsPerTask`. Setting `MaxDegreeOfParallelism = 1` must produce genuinely
  single-threaded behaviour, and bit-identical output.

## How the test fixtures work

The single most important testing rule in this repository:

> **Ground truth never comes from EasyImageSharp.** Every expected value is produced by an
> independent implementation — Pillow, NumPy, libjpeg, or a reference encoder written straight from
> the format specification.

Fixtures live under `tests/EasyImageSharp.Tests/Fixtures/<format>/` and every format folder has the
same shape:

| File | What it is |
|---|---|
| `<name>.<ext>` | the encoded fixture, written by an independent encoder or assembled byte by byte |
| `<name>.rgba` | ground truth: `width * height * 4` bytes of RGBA, row-major, top-left origin; multi-frame fixtures concatenate every frame in order |
| `<name>.expected.png` | an 8-bit RGBA rendering of the first frame, for eyeballing a diff |
| `manifest.json` | one entry per fixture: `name`, `file`, `width`, `height`, `frames`, `notes`, plus per-format header facts |

A manifest entry may carry an `expect` field naming the exception type the decoder is *required* to
throw — that is how "we deliberately do not implement this feature" is encoded as a test rather than
as a silent gap. `FixtureDecodeTests` walks every manifest and asserts the decode matches the `.rgba`
bytes exactly (or throws the named exception).

Fixtures are copied next to the test binaries by a `CopyToOutputDirectory` rule in the test csproj,
and read through the `FixturePath` helper. They are tracked in git as binary (`.gitattributes`).

## Regenerating fixtures

The generators are deterministic in what they *depict*: every pattern comes from a fixed seed and no
timestamps are written, so re-running them reproduces the same pixels.

They are **not** byte-reproducible across machines, and you should not expect them to be. The
expected-value files are PNGs written by Pillow, whose wheels compress with zlib-ng; its deflate
output changes with the zlib-ng version and with the SIMD path chosen at run time from the host CPU.
Regenerating on a different machine therefore rewrites hundreds of files that contain identical
pixels. CI does not check this, for the same reason.

```bash
cd tests/EasyImageSharp.Tests/Fixtures
python -m pip install "pillow>=11" "numpy>=2"
python generate.py
python check_determinism.py
```

**`check_determinism.py` is the check, not `git status`.** It copies `generate.py` and every
`gen_*.py` into a scratch directory, regenerates the whole corpus there from nothing, and compares the
result against the corpus on disk by the strongest rule that is stable for each kind of file: **decoded
pixels** for anything Pillow can open (mode, size, palette, frame count, the per-frame delay, dispose,
blend, rect and loop keys, and every frame's pixel array — every frame, not only the first), exact
bytes for `.rgba` ground truth and hand-assembled blobs, and a structural comparison for
`manifest.json` with the keys that hash or measure *encoded* bytes removed. It exits 0 when the corpus
agrees, 1 when it differs, and 2 when the check itself could not run. Over the corpus as it stands —
a little over 1,250 files — it takes about ten seconds.

```bash
python check_determinism.py --verbose            # name every file it compared
python check_determinism.py --json report.json   # machine-readable result, for CI
python check_determinism.py --scratch /tmp/fx    # keep the regenerated corpus for inspection
```

A dirty `git status` after `python generate.py` is **not** a determinism signal, and you should not try
to make it clean. It is recompression noise: Pillow's wheels deflate through zlib-ng, whose output
depends on the zlib-ng version and on the SIMD path chosen at run time from the host CPU, so hundreds
of pixel-identical files get rewritten. The earlier byte-comparing CI job flagged about 330 such files
and had to be deleted, which is exactly why the checker exists.

If `check_determinism.py` fails on a file nobody touched, suspect the toolchain — a Pillow major
version that changed a *decode* — before suspecting the corpus. Commit only the fixtures you actually
meant to change; reverting incidental recompression keeps the diff readable and the history honest.

`generate.py` is the entry point; it discovers and calls the per-area generators:

| Script | Produces |
|---|---|
| `generate.py` | PNG, BMP, TIFF, JPEG, GIF fixtures, and it drives all the others |
| `gen_apng.py` | APNG: 25 well-formed animations and 15 deliberately malformed ones, with per-frame RGBA |
| `gen_tiffadv.py` | advanced TIFF: CCITT, JPEG-in-TIFF, planar, tiled, the wide sample formats, BigTIFF |
| `gen_webp.py`, `gen_webpenc.py`, `gen_vp8enc.py` | WebP decode fixtures, plus source images for the encoder and VP8 tests |
| `gen_smallformats.py` | TGA, Netpbm (PBM/PGM/PPM/PAM), QOI, ICO/CUR |
| `gen_metadata.py` | EXIF, orientation, DPI, ICC, XMP, PNG text chunks, GIF frame facts |
| `gen_document.py` | synthetic text pages for skew, orientation, page detection, cleanup, layout |
| `gen_geometry.py` | resize-kernel, affine and perspective reference outputs |
| `gen_effects.py` | colour matrix, convolution, compositing and histogram references |
| `gen_drawing.py` | reference renderings for the annotation drawing tests |

If you add a fixture, add it to the relevant generator (never by hand), regenerate, and commit both
the generator change and the produced files in the same commit. If regenerating changes files you did
not mean to touch, your Pillow or NumPy version differs from the one the corpus was built with —
pin to Pillow 11 and NumPy 2 before assuming the generator is at fault.

QOI is a special case: Pillow does not support it, so `gen_smallformats.py` contains a small
reference encoder written directly from the specification. It doubles as the byte-for-byte oracle
for the library's own QOI encoder.

## The fuzz harness

`tests/EasyImageSharp.Tests/FuzzSmokeTests.cs` runs as part of the ordinary test suite. It is a
fixed-seed mutation fuzzer over every fixture file plus the library's own encoder output.

**What it asserts.** For every mutated input, `Image.Load` and `Image.Identify` may only:

- succeed, or
- throw `ImageFormatException` (any subclass), or
- throw `NotSupportedException`;

and each call must finish inside a 30-second timeout and allocate under 100 MB. Anything else — an
`IndexOutOfRangeException` escaping, an infinite loop, a multi-gigabyte allocation — is a failure.
That is the decoder contract, enforced mechanically.

**How it mutates.** Eight strategies: byte flips, random byte runs, truncation, insertion,
duplication, header-focused bit flips, and writing "interesting" 16- and 32-bit values (0, 1,
`0x7FFF`, `0x80000000`, `0xFFFFFFFF`, …) into the first 160-200 bytes where dimensions, offsets and
counts live.

**Reproducing a failure.** Failing inputs are written to
`<temp>/EasyImageSharp-fuzz/<seed>-<mutation>.bin` and the assertion message names the path. Copy
that file, add a decoder test to `CorruptInputTests.cs` asserting the correct exception, then fix the
decoder. Growing `CorruptInputTests` is how a fuzz finding becomes a permanent regression test.

**Running it deeper.** Two environment variables override the defaults; no source edit is needed.

| Variable | Default | Effect |
|---|---|---|
| `EASYIMAGESHARP_FUZZ_MUTATIONS` | `400` | mutations generated per seed file |
| `EASYIMAGESHARP_FUZZ_SEED` | `12345` | RNG seed for the mutation stream |

```bash
EASYIMAGESHARP_FUZZ_MUTATIONS=20000 EASYIMAGESHARP_FUZZ_SEED=$RANDOM \
  dotnet test tests/EasyImageSharp.Tests -c Release -f net10.0 --filter FuzzSmokeTests
```

The seed is parsed as a `long` and narrowed, so a CI run identifier — GitHub's `run_id` overflows
`Int32` — can be passed straight through instead of silently falling back to the default. The test
writes its effective configuration to the test output, saying for each value whether it came from the
environment or from the default, so a run that quietly ignored your variable is visible in the log. The
nightly workflow passes both.

The seed corpus is drawn from the PNG, APNG, BMP, TIFF, TGA, Netpbm, QOI and ICO manifests — the
deliberately malformed APNGs included — plus a handful of images this library's own encoders produce,
which reach filter and compression paths no third-party fixture does. The run prints the seed count and
a per-format outcome breakdown to the test output.

## Adding a codec

Codecs plug in through partial classes, so a new format touches almost nothing that already exists.

**1. Implement `IImageDecoder` and `IImageEncoder`** in `src/EasyImageSharp/Formats/<Format>/`.

```csharp
public sealed class MyFormatDecoder : IImageDecoder
{
    public Image<TPixel> Decode<TPixel>(ReadOnlySpan<byte> data, DecoderOptions options)
        where TPixel : unmanaged, IPixel<TPixel>
    {
        // Parse the header first, then, BEFORE allocating any pixel memory:
        options.EnsureFrameWithinLimits(width, height, "MyFormat");
        ...
    }

    public ImageInfo Identify(ReadOnlySpan<byte> data, DecoderOptions options) { ... }
}
```

Three obligations, all of which the fuzz harness will check:

- **Enforce the limits before allocating.** Call `DecoderOptions.EnsureFrameWithinLimits` immediately
  after the header is parsed. `Identify` is never subject to size limits — callers use it precisely
  to decide whether they want to decode at all.
- **Honour `DecoderOptions.MaxFrames`** if the format is multi-frame.
- **Respect the exception contract.** Malformed input throws `InvalidImageContentException`;
  a recognised but unimplemented feature throws `NotSupportedException`. Wrap span-parsing accidents
  with the shared helper rather than letting framework exceptions escape:

```csharp
catch (Exception ex) when (DecoderGuard.IsMalformedInputSymptom(ex))
{
    throw DecoderGuard.Wrap("MyFormat", ex);
}
```

**2. Register the format** by adding a partial file `src/EasyImageSharp/Formats/ImageFormat.MyFormat.cs`.
Use the nested-holder pattern so the instance is created on first use and does not depend on
static-initializer ordering across partial files:

```csharp
public sealed partial class ImageFormat
{
    /// <summary>The MyFormat format.</summary>
    public static ImageFormat MyFormat => MyFormatHolder.Value;

    private static class MyFormatHolder
    {
        public static readonly ImageFormat Value = new(
            "MYFORMAT", "image/myformat", new[] { "mf" },
            static data => data.Length >= 4 && data[..4].SequenceEqual("MYF!"u8),
            static () => new MyFormatDecoder(), static () => new MyFormatEncoder());
    }
}
```

Then add it to `ImageFormat.All` in `ImageFormat.cs`. **Order matters:** `All` is the detection
order, so a format whose signature is a prefix of another format's signature must come *after* it.

**3. Add `SaveAsMyFormat` extensions** in a new partial file of `ImageExtensions`
(`src/EasyImageSharp/ImageExtensions.MyFormat.cs`), mirroring the stream/path/async trio the other
formats offer.

**4. Add fixtures and tests.** Extend the relevant generator (probably `gen_smallformats.py`) with
independently-encoded samples plus `.rgba` ground truth, add round-trip tests, and add crafted
corrupt inputs to `CorruptInputTests`. The fuzz harness picks up the new format automatically once
its folder is listed in `FuzzSmokeTests.CollectSeeds`.

**5. Review the public API surface** — see [Public API changes](#public-api-changes).

## Adding a processing operation

The processing pipeline is one `IImageProcessingContext` interface spread over partial files by
subject area. Adding an operation is four small edits in the same area folder:

| Step | File | What goes in it |
|---|---|---|
| 1 | `IImageProcessingContext.<Area>.cs` | the interface member, with XML docs describing the contract |
| 2 | `ImageProcessingContext.<Area>.cs` | the implementation, usually delegating to a static `<Area>Ops` class |
| 3 | `<Name>Ops.cs` | the actual pixel work, as `static` methods over `ImageFrame<TPixel>` |
| 4 | `ProcessingExtensions.<Area>.cs` | convenience overloads with defaults |

Existing areas are `Processing/` (core), `Processing/Document/`, `Processing/Effects/`,
`Processing/Transforms/`, `Processing/Quantization/`, `Processing/Metadata/` and `Drawing/`. Put a new
operation in the area it belongs to; create a new area only if none fits, and then create all four
files plus a folder.

Rules for the pixel work itself:

- Operations apply to **every frame** of the image unless the operation is explicitly root-frame-only
  (layout and detection operations like `SegmentText` and `DetectSkew` are, and say so in their docs).
- Go through `ParallelRowIterator` for row-parallel work so `Configuration` is honoured.
- Rent scratch buffers from `ArrayPool<T>.Shared` and return them in a `finally`.
- Operations that only make sense on luminance should convert internally rather than refusing colour
  input, and say so in the XML docs — that is what the document operations do.
- The result must be **deterministic and independent of the degree of parallelism**. A row-parallel
  operation that produces different bytes at `MaxDegreeOfParallelism = 1` is a bug.

Then add a test with independently-computed expected output. For anything with a NumPy or Pillow
equivalent, add a fixture to `gen_effects.py` or `gen_geometry.py` rather than hard-coding numbers in
C#.

## Public API changes

The public surface is the package's contract: once a member ships, removing or changing it breaks
every caller and can only happen in a major release. Treat additions as deliberate, not incidental.

**Adding API.** Ask whether it needs to be public at all. `internal` plus `InternalsVisibleTo` for the
test project covers most helpers, and anything public has to be documented, kept working and supported
indefinitely. Public members need XML documentation — the packages ship a documentation file.

**Removing or changing API.** A rename, a changed parameter type, a removed overload and a changed
default are all breaking. Say so explicitly in the pull request and in `CHANGELOG.md`, and expect it to
wait for the next major version.

**How it is enforced.** `Microsoft.CodeAnalysis.PublicApiAnalyzers` tracks the surface as text files in
the repository, one pair per target framework:

```
src/EasyImageSharp/PublicAPI/net8.0/PublicAPI.Shipped.txt      the surface that has already shipped
src/EasyImageSharp/PublicAPI/net8.0/PublicAPI.Unshipped.txt    additions since the last release
src/EasyImageSharp/PublicAPI/net10.0/...                       the same pair for the other framework
src/EasyImageSharp.AI/PublicAPI/...                            and the same four files for the add-on
```

Every public member must appear in one of them. `RS0016` fails the build on a member that appears in
neither, so this is enforced by the compiler rather than by review: add your new members to
`PublicAPI.Unshipped.txt` **for both target frameworks**, unless the member genuinely exists on only
one. The analyzer ships a code fix (`Add to public API`, with `Fix All` over the project), or:

```bash
dotnet format analyzers src/EasyImageSharp/EasyImageSharp.csproj --diagnostics RS0016 --severity warn
```

A removal is a `*REMOVED*` line carrying the old signature, and is breaking. At release time the
unshipped entries are promoted into `PublicAPI.Shipped.txt`, in the same commit as the version bump and
the `CHANGELOG.md` section. The full generation and verification procedure — including how to prove a
baseline really matches the assemblies that were published, with `apicompat --enable-strict-mode`
against the previous `.nupkg` — is in
[`src/EasyImageSharp/PublicAPI/README.md`](src/EasyImageSharp/PublicAPI/README.md).

**In review**, call out any diff that adds a `public` type or member so the decision is conscious. The
`PublicAPI.Unshipped.txt` diff is the shortest description of what a pull request adds to the contract.

## Samples and deployment smokes

Two sample projects exist to prove claims an ordinary `dotnet build` cannot. Both take no arguments,
synthesise their own input, print one line per check and exit non-zero if any check fails, so CI only
has to look at the exit code. Run them from the repository root.

**Native AOT.** `samples/AotSmoke` walks every codec, every metadata path and every processing stage,
because AOT failures surface as a missing metadata token at run time rather than as a build error:

```bash
dotnet run     --project samples/AotSmoke -c Release
dotnet publish samples/AotSmoke -c Release -p:PublishAot=true -o artifacts/aot-smoke
./artifacts/aot-smoke/AotSmoke          # the published native binary must also exit 0
```

The publish must emit no `IL2xxx` or `IL3xxx` warning. Running the *published* binary is the part that
matters: an unpublished run proves only that the code works on the JIT.

**Trimming.** `samples/Thumbnailer` publishes self-contained and trimmed with the SDK's default
suppressions turned off, which is stricter than any ordinary build:

```bash
dotnet publish samples/Thumbnailer -c Release -r linux-x64 --self-contained true \
  -p:PublishTrimmed=true -p:TrimmerSingleWarn=false -p:SuppressTrimAnalysisWarnings=false \
  -o artifacts/trim-smoke
./artifacts/trim-smoke/Thumbnailer
```

A single `warning IL####` line fails it, because `TreatWarningsAsErrors` is inherited from the root
`Directory.Build.props`. Substitute your own RID for `linux-x64`.

If you add a public entry point that reflects, serialises, or parses an enum by name, add a check to
`samples/AotSmoke` in the same pull request. That is where such a change gets caught.

## Benchmarks

`benchmarks/EasyImageSharp.Benchmarks` is a BenchmarkDotNet suite, and it is the only source of the
figures in the README's Performance table. Its corpus is **generated, not committed**: a script rebuilds
it from nothing, so every row is a claim a reviewer can check on their own hardware.

```bash
python -m pip install "pillow>=11" "numpy>=2"
python benchmarks/corpus/generate.py
dotnet run -c Release -f net10.0 --project benchmarks/EasyImageSharp.Benchmarks -- --filter "*"
dotnet run -c Release -f net10.0 --project benchmarks/EasyImageSharp.Benchmarks -- --readme-table
```

The last command runs nothing. It reads the JSON reports the previous run left under
`benchmarks/BenchmarkDotNet.Artifacts/` and regenerates `benchmarks/results/README-performance.md`,
which is the table the README carries. If a benchmark a README row maps to has been renamed, it exits
non-zero naming the missing benchmark, so a row cannot go missing quietly.

While iterating, narrow the run — the arguments are BenchmarkDotNet's own:

```bash
# one class, or one method and parameter value
dotnet run -c Release -f net10.0 --project benchmarks/EasyImageSharp.Benchmarks -- --filter "*DecodeBenchmarks*"

# every benchmark runs exactly once: proves the suite executes, and the timings mean nothing
dotnet run -c Release -f net10.0 --project benchmarks/EasyImageSharp.Benchmarks -- --filter "*" --job Dry
```

`--job Dry` is what CI runs, and it is the right thing to run locally after adding a benchmark, before
spending twenty minutes on a real measurement.

**What is reproducible and what is not.** Absolute milliseconds belong to the machine that produced
them and will not match yours. The corpus definition, the set of operations measured and the
`Allocated` column are reproducible, and a ratio between two runs on the same machine is the only
performance claim worth putting in a pull request. Quote the hardware and the runtime version alongside
any number you report. What each README row maps to is documented in
[`benchmarks/README.md`](benchmarks/README.md).

Some questions are per-target-framework and have to be measured on both. `InflateBenchmarks` exists
because .NET 8's `ZLibStream` wraps classic native zlib while .NET 10's wraps zlib-ng, and the library's
managed inflater is the right choice on the first and the wrong one on the second. If you touch a path
where the runtime's own implementation may differ between the two, run `-f net8.0` and `-f net10.0`
before concluding anything.

## Submitting a pull request

Before you open it:

- [ ] `dotnet build EasyImageSharp.slnx -c Release` is **warning-free**
- [ ] `dotnet test EasyImageSharp.slnx -c Release` is green on **net8.0 and net10.0**
- [ ] New behaviour has a test whose expected values came from somewhere other than this library
- [ ] Public API additions are in `PublicAPI.Unshipped.txt` for **both** target frameworks and carry XML documentation
- [ ] Fixtures, if touched, were regenerated by their script and `python check_determinism.py` reports no differences
- [ ] A new C# block in `README.md` was transcribed into `tests/EasyImageSharp.Tests/ReadmeSamplesCompileTests.cs`
- [ ] `CHANGELOG.md` has an entry under `## [Unreleased]` for anything user-visible

Keep commits focused; a codec, a set of fixtures and a refactor belong in separate commits. Write
commit messages in the imperative mood, describing the effect rather than the mechanics
("Reject negative PNG chunk lengths" rather than "fix bug in decoder").

Pull requests need a green CI run on all three operating systems before review. If CI fails only on
macOS or only on `net8.0`, that is a real finding about your change, not a flaky runner.

### What gets a fast review

Small, focused changes with tests. Bug fixes that arrive with the crafted input that triggered them.
Codec work that comes with fixtures.

### What needs discussion first

Open an issue before starting on: a new public type or namespace, a new package reference, a change
to the exception contract or `DecoderOptions`, anything that changes the byte output of an existing
encoder, and anything that would make the library depend on native code. These are cheap to discuss
and expensive to unwind.
